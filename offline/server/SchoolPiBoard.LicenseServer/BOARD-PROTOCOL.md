# Подписка онлайн-доски: протокол

Как онлайн-доска (`board.school-pi.online`) продаёт подписку через этот
сервис. Доска не знает паролей Робокассы и никогда не обращается к ней
напрямую — это правило владельца, и оно не обсуждается.

Магазин офлайн-лицензий работает как прежде: у счетов появился вид
(`kind`), и у всех прежних он `license`. Ни один старый путь не изменён.

## Кто что делает

```
доска                          сервис ключей                Робокасса
  │  «счёт: пользователь 12,      │                              │
  │   тариф standard, 90 дн.,     │                              │
  │   490 ₽»                      │                              │
  ├──── POST /board/invoice ─────►│ заводит счёт своим номером    │
  │◄──── paymentUrl ──────────────┤                              │
  │                               │                              │
  │  человек уходит платить ─────────────────────────────────────►│
  │                               │◄──── ResultURL ──────────────┤
  │                               │ помечает счёт оплаченным      │
  │◄──── POST callback ───────────┤                              │
  │  продлевает подписку          │                              │
```

Номер счёта выдаёт только сервис ключей: у Робокассы он один на магазин,
и вторая нумерация однажды выдала бы занятый номер — человек заплатил бы
на счёт, которого сервис не знает.

## Подпись

Обе стороны подписывают тело запроса общим секретом (`BOARD_SHARED_SECRET`
здесь, `LICENSE_SHARED_SECRET` на доске — значение одно и то же).

```
X-Timestamp: 1788000000            секунды Unix
X-Signature: <hex>                 HMAC-SHA256(secret, timestamp + "." + body)
```

Подпись старше пяти минут не принимается: иначе перехваченный запрос
можно было бы повторять сколько угодно. Сравнение — постоянного времени.

Секрет не задан — эндпоинты `/board/*` отвечают 404: открытый эндпоинт,
выставляющий счета от чужого имени, не должен существовать «на всякий
случай».

## `POST /board/invoice`

Доска просит счёт.

```json
{
  "userId": 12,
  "email": "teacher@example.com",
  "planCode": "standard",
  "planName": "Стандартный",
  "days": 90,
  "amount": 490,
  "autoRenew": true
}
```

`days` — только 30, 90, 180 или 365. `amount` — в рублях, считает доска:
цены лежат в её базе. `autoRenew` помечает счёт разрешающим повторные
списания; решить это можно лишь при первой оплате — Робокасса не даёт
пометить счёт задним числом.

Ответ:

```json
{ "invoiceId": "1042", "paymentUrl": "https://auth.robokassa.ru/...", "amount": "490.00" }
```

Доска отправляет человека по `paymentUrl`.

## Обратный вызов доске

После оплаты сервис ключей зовёт `Board:CallbackUrl` (например
`https://board.school-pi.online/api/billing/callback`) с той же подписью:

```json
{
  "invoiceId": "1042",
  "userId": 12,
  "planCode": "standard",
  "days": 90,
  "amount": 490,
  "autoRenew": true,
  "paidAt": "2026-09-02T10:00:00Z"
}
```

Доска обязана быть готова к повтору: тот же `invoiceId` не должен
продлевать срок дважды. Ответ 2xx означает «принято»; при любом другом
ответе или недоступности сервис ключей повторит попытку — раз в пять
минут, пока не примут. Деньги уже взяты, и терять оплату нельзя.

## `POST /board/recurring`

Автопродление. Когда продлевать — решает доска: сроки знает она.

```json
{
  "userId": 12,
  "planCode": "standard",
  "planName": "Стандартный",
  "days": 90,
  "amount": 490,
  "previousInvoiceId": 1042
}
```

Сервис ключей заводит новый счёт и просит Робокассу списать по карте,
которой платили в первый раз. Форма покупателю не показывается. Списание
принято — ответ `{ "invoiceId": "1105" }`; об оплате доска узнает обычным
обратным вызовом, как после ручной оплаты. Отказ — 402.

Списание по чужому или неоплаченному счёту не выполняется никогда: это
чужая карта.

## Настройки

| Переменная | Что это |
|---|---|
| `BOARD_SHARED_SECRET` | общий секрет; на доске он же `LICENSE_SHARED_SECRET` |
| `Board:CallbackUrl` | куда сообщать об оплате |
| `Robokassa:RecurringUrl` | адрес повторных списаний, по умолчанию адрес Робокассы |

## Что осталось проверить живой оплатой

Состав чека в повторном списании намеренно не передаётся: место `Receipt`
в подписи рекуррентного запроса на живой оплате не проверено, а неверная
подпись даёт отказ, который выглядит как поломка магазина. Для повторных
списаний чек формирует Робокасса по данным первого платежа. Если
окажется, что чек нужен и здесь — это одна строка в
`RobokassaService.ChargeRecurringAsync`.
