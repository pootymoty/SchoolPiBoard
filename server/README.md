# Whiteboard Server

Сервис лицензий десктопной версии **и** бэкенд веб-версии — один проект,
как и предполагает ТЗ Фазы 2. Имя `Whiteboard.LicenseServer` осталось
с Фазы 1; переименовывать его сейчас — лишний шум в истории.

Что умеет:

- десктопные лицензии: выпуск ключа после оплаты, привязка к двум устройствам,
  периодическая проверка, пробный период;
- веб-версия: учётные записи, подписки, доски, участники и роли,
  комната доски в реальном времени через SignalR.

Стек: ASP.NET Core 8 (minimal API + SignalR) + PostgreSQL (EF Core / Npgsql)
+ Redis (backplane SignalR и присутствие участников).

## Модель лицензии

- Разовая оплата → один перманентный ключ формата `XXXX-XXXX-XXXX-XXXX`, без срока действия.
- Ключ живёт максимум на **2 устройствах** одновременно (значение настраивается: `License:DeviceLimit`).
- Клиент проверяется онлайн при активации и раз в сутки в фоне; без интернета
  приложение работает ещё 14 дней (грейс-период считает клиент).
- До покупки — **пробный период 3 дня**, один раз на компьютер. Решение о выдаче
  принимает сервер: локальные метки на компьютере стираются переустановкой,
  запись в базе — нет.

## Запуск

```bash
cd server/Whiteboard.LicenseServer

export ConnectionStrings__Postgres="Host=localhost;Database=whiteboard_licenses;Username=postgres;Password=postgres"
export LICENSE_TOKEN_SECRET="$(openssl rand -hex 32)"
export STRIPE_WEBHOOK_SECRET="whsec_..."
export SENDGRID_API_KEY="SG...."
export SendGrid__FromEmail="noreply@ваш-домен"
export License__DownloadUrl="https://ваш-домен/download/Whiteboard.exe"

dotnet run
```

Схема базы применяется при старте (`sql/001_init.sql`, идемпотентный скрипт),
отдельная команда миграции не нужна.

| Переменная | Обязательна | Зачем |
|---|---|---|
| `ConnectionStrings__Postgres` | да | подключение к PostgreSQL |
| `LICENSE_TOKEN_SECRET` | да | секрет подписи токенов активации (HMAC-SHA256) |
| `STRIPE_WEBHOOK_SECRET` | в Production | проверка подписи вебхука Stripe |
| `SENDGRID_API_KEY` | в Production | отправка письма с ключом |
| `SendGrid__FromEmail` | в Production | адрес отправителя, подтверждённый в SendGrid |
| `License__DownloadUrl` | нет | ссылка на EXE в письме |
| `License__SupportEmail` | нет | адрес поддержки в письме |
| `License__DeviceLimit` | нет | сколько устройств на ключ (по умолчанию 2) |
| `Robokassa__MerchantLogin` | для продаж | идентификатор магазина |
| `ROBOKASSA_PASSWORD1` | для продаж | пароль №1 — подпись ссылки на оплату |
| `ROBOKASSA_PASSWORD2` | для продаж | пароль №2 — проверка уведомления об оплате |
| `Robokassa__Amount` | нет | цена лицензии, по умолчанию 15000.00 |
| `Robokassa__IsTest` | нет | тестовый режим Робокассы |
| `Robokassa__SendReceipt` | нет | передавать состав чека (см. ниже) |
| `Trial__Days` | нет | длительность пробного периода, по умолчанию 3 |
| `Trial__OneTrialPerEmail` | нет | считать повтором ту же почту, по умолчанию true |
| `Web__SiteUrl` | нет | адрес страницы покупки — в сообщениях об ошибке |
| `Web__AllowedOrigins__0` | нет | домен сайта для CORS (нужен только для JSON-запросов) |
| `AUTH_TOKEN_SECRET` | в Production | секрет подписи токенов входа в веб-версию |
| `REDIS_CONNECTION_STRING` | в Production | backplane SignalR и присутствие участников |
| `Web__AppOrigins__0` | для веб-версии | домен веб-приложения (CORS + WebSocket) |
| `Auth__TokenLifetimeDays` | нет | срок жизни токена входа, по умолчанию 30 |
| `Auth__SubscriptionTrialDays` | нет | пробный период подписки, по умолчанию 7 |

В режиме Development сервис поднимается и без Stripe/SendGrid: подпись вебхука
не проверяется, а письмо пишется в лог. В Production отсутствие любого из
секретов — ошибка старта, чтобы сервис не работал «наполовину».

## Эндпоинты

### `POST /license/activate`

```json
{ "key": "ABCD-EFGH-JKMN-PQRS", "hardwareId": "8F2C…" }
```

| Ответ | Когда |
|---|---|
| `200 { token, key, email, activatedAt, devicesUsed, deviceLimit }` | слот занят этим устройством (в том числе повторно) |
| `400 { error: "bad_request" }` | ключ не той длины/формата |
| `403 { error: "invalid_key" }` | ключа нет или он отозван |
| `409 { error: "device_limit", devicesUsed, deviceLimit }` | все слоты заняты другими устройствами |

`token` — JWT (HS256) без даты истечения, с полем `issuedAt`. Клиент хранит его
как есть и не разбирает; подпись проверяет сервер.

Проверка лимита выполняется в транзакции с `SELECT … FOR UPDATE` по строке
лицензии — два одновременных запроса не смогут занять третий слот.

### `POST /license/validate`

Тело то же. Всегда `200`:

```json
{ "valid": true, "reason": "ok", "devicesUsed": 1, "deviceLimit": 2 }
```

Отдельный код ошибки здесь был бы вреден: клиенту важно отличать «сервер сказал
нет» (блокировать приложение) от «до сервера не достучались» (продолжать работу).

### `POST /license/deactivate`

Освобождает слот устройства — нужно при переезде на новый компьютер.
`200 { ok: true }`, если слот освобождён или его уже не было.

### `POST /webhook/stripe`

Принимает `checkout.session.completed` и `payment_intent.succeeded`, выпускает
ключ и синхронно отправляет письмо через SendGrid.

- Подпись проверяется по схеме Stripe (`t=…,v1=…`, HMAC-SHA256, окно 5 минут).
- В базе хранится **только SHA-256 от payment intent id** — ни идентификатора
  платежа, ни тем более карточных данных.
- Повторная доставка того же события не создаёт вторую лицензию (уникальный
  индекс по хешу платежа), а если письмо в прошлый раз не ушло — сервис вернёт
  `500`, и Stripe повторит попытку.

### `POST /trial/start`

```json
{ "hardwareId": "8F2C…", "email": "user@example.com" }
```

| Ответ | Когда |
|---|---|
| `200 { status: "started", startedAt, expiresAt, days }` | период выдан впервые |
| `200 { status: "resumed", … }` | период уже шёл — отдаём остаток, а не новые дни |
| `409 { error: "trial_used", expiresAt }` | этот компьютер (или эта почта) период уже использовал |
| `400 { error: "bad_request" }` | почта или идентификатор устройства не приняты |

Переустановка приложения посреди пробного периода не начинает отсчёт заново:
сервер возвращает ту же дату окончания.

### `POST /purchase/start`

Принимает и обычную форму (`email=…`), и JSON (`{ "email": "…" }`).

- Форме отвечает `302` на страницу оплаты Робокассы — поэтому странице сайта
  не нужен ни JavaScript, ни CORS.
- JSON-запросу отвечает `200 { paymentUrl, invoiceId, amount }`.
- Если Робокасса не настроена — `503`.

### `POST|GET /payment/robokassa/result`

ResultURL Робокассы. Проверяет подпись на Password2, выпускает ключ,
отправляет письмо и отвечает строкой `OK{InvId}` — иначе Робокасса
считает уведомление недоставленным и повторяет его.

Повторное уведомление о том же счёте лицензию не дублирует.

## Веб-версия

### Учётные записи

```
POST /auth/register   { email, password, displayName }  -> { token, user, subscription }
POST /auth/login      { email, password }               -> { token, user, subscription }
GET  /auth/me                                           -> { user, subscription }
```

Пароли хранятся как PBKDF2-HMAC-SHA256 (210 000 итераций), параметры лежат
рядом с хешем — их можно поднять, не ломая уже заведённые пароли. Токен
входа — обычный JWT со сроком; секрет у него отдельный от лицензионного,
чтобы утечка одного не давала подделать другое.

При регистрации сразу заводится пробная подписка на 7 дней.

### Доски и участники

```
GET    /boards
POST   /boards                                { name }
GET    /boards/{id}
DELETE /boards/{id}
GET    /boards/{id}/members
POST   /boards/{id}/members                   { email, role }
PATCH  /boards/{id}/members/{userId}          { role }
DELETE /boards/{id}/members/{userId}
```

Роли: `owner` (создатель — управляет составом и может удалить доску),
`editor` (рисует), `viewer` (только смотрит). Роль всегда берётся одним
методом `BoardService.GetRoleAsync`, и REST, и хаб спрашивают именно его —
иначе правила доступа неизбежно разъехались бы между ними.

Пригласить можно только зарегистрированного пользователя: ссылки-приглашения
без регистрации вынесены за рамки Фазы 2. Подписка требуется владельцу для
создания досок; приглашённым участникам — нет, иначе учитель не смог бы
позвать класс.

### Комната доски: `/hub/board` (SignalR)

```
Клиент -> сервер:   JoinBoard(boardId), LeaveBoard(boardId), CursorMove(boardId, x, y)
Сервер -> клиентам: UserJoined, UserLeft, CursorMoved
```

`JoinBoard` возвращает состояние комнаты целиком: доску, роль, участников
и список доступа. Тот же вызов используется после переподключения — клиент
не «догоняет» пропущенные события, а получает актуальное состояние заново.

Токен передаётся строкой запроса `access_token` (WebSocket не умеет слать
заголовок Authorization); сервер принимает его только для адреса хаба.

Присутствие живёт в Redis: хеш на доску, поле — идентификатор соединения,
у ключа есть срок жизни, чтобы упавший инстанс не оставлял «призраков».
Без Redis сервис поднимается только в Development и работает в одном процессе.

### Подписка

```
GET  /billing/status
POST /billing/create-checkout-session   -> 503, пока не подключена оплата
POST /billing/webhook
```

**Открытый вопрос.** В ТЗ Фазы 2 подписка описана через Stripe Checkout, но
в Фазе 1 выяснилось, что продавцу со статусом самозанятого Stripe недоступен
(см. `docs/payment-legal-notes.md`). Поэтому сейчас реализовано всё, что
от платёжной системы не зависит: пробный период, состояние подписки и её
проверка при создании доски. Подключение оплаты — одна точка,
`Endpoints/Web/BillingEndpoints.cs`.

`200 { "status": "ok" }`.

## Настройка Робокассы

В личном кабинете магазина:

1. **ResultURL** — `https://ваш-домен/payment/robokassa/result`, метод POST.
   Именно по нему сервис узнаёт об оплате; браузеру покупателя в этом
   вопросе не верим вовсе.
2. **SuccessURL** и **FailURL** — страницы вашего сайта («спасибо, ключ
   отправлен на почту» и «оплата не прошла»). Сервер лицензий в них не участвует.
3. Пароли №1 и №2 — в переменные `ROBOKASSA_PASSWORD1` и `ROBOKASSA_PASSWORD2`.
4. Пока идёт проверка — `Robokassa__IsTest=true`: деньги не списываются,
   а весь путь до выдачи ключа работает по-настоящему.

### Про чек

`Robokassa__SendReceipt` по умолчанию **выключен**. Для самозанятого чек, как
правило, формирует сама Робокасса, и передавать состав чека параметром
`Receipt` не требуется. Включайте флаг только если в кабинете включена
фискализация с составом чека — тогда состав берётся из `Robokassa:Description`,
`Amount`, `TaxSystem` (`npd`) и `Tax` (`none`).

Важная деталь на случай отладки: в подпись ссылки на оплату входит **уже
закодированная** строка `Receipt`, ровно в том виде, в каком она уходит
в адресе. Это самое частое место ошибки при интеграции — если Робокасса
отвечает «неверная подпись» с включённым чеком, смотреть надо сюда
(`RobokassaService.BuildPaymentUrl`).

## Ограничение частоты

Fixed window по IP-адресу: `/license/activate`, `/license/deactivate`,
`/trial/start` и `/purchase/start` — 10 запросов в минуту,
`/license/validate` — 60. Превышение → `429`.

За обратным прокси включите `UseForwardedHeaders` с указанием доверенных
адресов (`KnownProxies`/`KnownNetworks`), иначе все клиенты будут выглядеть
как один IP прокси и делить общий лимит.

## Эксплуатация

Отозвать ключ (клиент заблокируется при следующей фоновой проверке):

```sql
UPDATE licenses SET revoked = true WHERE key = 'ABCD-EFGH-JKMN-PQRS';
```

Освободить слот руками:

```sql
DELETE FROM license_activations
 WHERE license_id = (SELECT id FROM licenses WHERE key = 'ABCD-EFGH-JKMN-PQRS');
```

Посмотреть, кто брал пробный период:

```sql
SELECT email, started_at, expires_at FROM trial_activations ORDER BY started_at DESC LIMIT 20;
```

Выдать пробный период повторно (например, человек сменил компьютер и просит):

```sql
DELETE FROM trial_activations WHERE email = 'user@example.com';
```

Выпустить тестовый ключ без оплаты (PostgreSQL 13+):

```sql
INSERT INTO licenses (id, key, email, created_at, revoked)
VALUES (gen_random_uuid(), 'ABCD-EFGH-JKMN-PQRS', 'test@example.com', now(), false);
```

В ключе используются только символы `ABCDEFGHJKMNPQRSTUVWXYZ23456789` —
без `I`, `L`, `O`, `0` и `1`, чтобы ключ можно было продиктовать по телефону.

## Проверка связки с клиентом

Адрес сервера в десктопном приложении берётся из переменной окружения
`WHITEBOARD_LICENSE_URL` (перекрывает всё), иначе из `LicenseServerUrl`
в `%APPDATA%\WhiteboardApp\settings.json`.

```powershell
$env:WHITEBOARD_LICENSE_URL = "http://localhost:5000"
.\Whiteboard.exe
```

## Чего здесь намеренно нет

- Личного кабинета и админки: отозвать ключ и освободить слот проще запросом в базу.
- Очереди писем: одно письмо на оплату, синхронной отправки с повтором от Stripe достаточно.
- Защиты от подбора ключей с распределённого ботнета: ограничитель работает по IP.
  Перебор 16 символов из алфавита в 31 знак (~79 бит) и так не имеет смысла.
